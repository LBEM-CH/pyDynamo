# pyDynamo design: a drop-in for Dynamo users

pyDynamo re-implements Dynamo 1.1.514 by reverse engineering it. Every behaviour comes from Dynamo's source (cited as file:line in the code) and is confirmed against Dynamo's own output. Nothing is invented. The detailed specifications and benchmark records are kept outside the public repository.

## The user and the workflow (requirements)

1. **Who the user is:** a Dynamo user, who knows Dynamo's commands, GUI and project folders.
2. **Why they switch:** to make the same runs faster, on GPUs, without MATLAB.
3. **How they activate it:** they turn pyDynamo on and off like any Python environment, without conda. While it is active, the Dynamo commands they use run pyDynamo.
4. **Making the inputs:** they run the same console steps as in Dynamo, for example `dtrandomize_azimuth` and `daverage`, to make the reference `.em` and the particle `.tbl`.
5. **Making the project:** they create it with `dcp.new`, edit it in the dcp GUI, then check and unfold it.
6. **Running it:** they run `./<project>.exe`.
7. **The unfolded project:** it is a folder exactly like Dynamo's, with `settings/`, `cards/`, `results/`, `temp/`, `log.txt` and `next_iteration.txt`.
8. **During the run:** each iteration's starting values and results are written into the project folder, at the same moments and under the same names as Dynamo writes them.

**Rule for the output:** the output must be exactly Dynamo's. That means:
- no extra pyDynamo files in the project folder;
- `log.txt` line for line, except values that also differ between two Dynamo runs (dates, durations, GPU model);
- the `.exe` byte-identical to the one Dynamo writes;
- tables and averages bit-identical to Dynamo's on the same GPU model (with adaptive_bandpass = 1, the reference-2
  realignment, pydyn/dalign.py, is bit-identical to Dynamo on the same machine; Dynamo's own result for that step
  varies between machines by up to about 1e-12; box sizes that are not a power of two are not verified).

## How each requirement is met, and what is missing

| # | Requirement | Status | Gap or work item |
|---|---|---|---|
| 1, 4 | Dynamo console functions under Dynamo's names and argument style | **Done.** `from pydyn import *` gives `dread`, `dwrite`, `dtrandomize_azimuth`, `daverage`, `dcp`, `dvput`, `dvcheck`, `dvunfold`, `dvload`, `dveo`, `dmask` and the viewers. MATLAB-style name/value pairs work, e.g. `dcp.new('myproject','d','particles_data','template','template.em','masks','default','t','particles.tbl');` (the trailing `;` is valid Python). `pydynamo` alone opens a Python console with these commands loaded. From the shell: `dtrandomize_azimuth --i IN.tbl --o OUT.tbl` and `daverage --d DATA --t TABLE.tbl --o AVERAGE.em`. | End-to-end acceptance test (below). |
| 2 | Same runs, faster, on GPUs, without MATLAB | **Done.** `--engine exact` (default; `$PYDYN_ENGINE` can change it) runs Dynamo 1.1.514's own CUDA kernels (PTX extracted at run time from the local Dynamo installation, `$PYDYN_DYNAMO_ROOT`) with cuFFT 8 and cuBLAS 8 (`$PYDYN_CUDA8_LIB`): bit-identical to the official engine on the same GPU model; `--exact-sms N` reproduces the cuBLAS 8 reduction order of a GPU with N SMs (e.g. 64 for an RTX A5000). Orientations are processed in batches of 128 with the same operations; the batched reductions and the merged steps are checked against legacy cuBLAS 8 and Dynamo's kernels on the GPU at start and switched off (same bits) if a check fails; `$PYDYN_EXACT_OPTS` turns steps off. Averages follow Dynamo's single-thread MATLAB: sequential double sums, particles in ascending tag order chained through the GPU workers, FFTW 3 for `fftn`/`ifftn` (`pydyn/matlab_numerics.py`; the system FFTW gives the same bits as MATLAB's), and MATLAB's sin/cos/atan2/acos through a port of fdlibm (`pydyn/fdlibm.py`). No MATLAB library is loaded. | Without an FFTW 3 library (`$PYDYN_FFTW_LIB`, else the system's `libfftw3.so.3`) NumPy FFTs are used and the averages are not bit-identical (a stderr note says so). `--engine fast`, the older CuPy engine, is close to Dynamo but not identical. |
| 3 | Activation as a plain, free environment named `pydynamo` (no conda) | **Done.** `.envs/pydynamo` is a `uv` venv: python-build-standalone CPython 3.11.18 and exact wheel versions with sha256 hashes from `requirements/pydynamo-lock.txt`, created by `requirements/recreate.sh` (steps in `requirements/README-env.txt`); pydyn is installed editable. Activate with `source .envs/pydynamo/bin/activate`, leave with `deactivate`; `prototype/bin/pydynamo-shell` opens a clean shell with the environment active. The console scripts restart themselves once in a clean environment, so `PYTHONPATH`/`LD_LIBRARY_PATH` of a login environment (for example an SBGrid-style software tree) cannot leak in. | — |
| 5 | `dcp.new` opens the GUI; `dcp` in a terminal opens the GUI; check and unfold from the GUI | **Done.** `dcp.new` opens the window by default (`gui` defaults to 1), as in Dynamo. Check, unfold, the mask editor (cylinder masks, `pydyn.masks`) and the Multireference menu (Create an even/odd project; Adaptive filtering: Derive a project, Edit parameters for Adaptive Filtering run, Plot attained resolution FSC for all iterations) are ported. | Not ported (`NotImplementedError`): other mask types, blank and random tables, the random and Fourier-compensation options of "average all", database queries and `*` selections in file boxes, the plugin manager, the show/progress/rewind/reset windows. |
| 5 | GUI on a published UI framework, quick to start, opened on the machine's own desktop session (no ssh tunnel) | **Done.** `pydyn.webui` (a package in `pyproject.toml`, with its static files as package data): an HTML view (Bootstrap 5.3.3 and Bootstrap Icons 1.11.3, vendored, sha256 in `static/vendor/MANIFEST.txt`) in a Qt WebEngine window (PySide6 6.11.3), over a local server bound to 127.0.0.1 that requires a per-session token; all logic stays in `pydyn/dcpcontrol.py`. One window: Dynamo's steps in a sidebar with their enabled/correct state, each step's window as a page, the message list, dialogs for the mask editor, the adaptive-bandpass parameters and a file chooser, and Dynamo's View and Multireference menus. `dcp --p NAME --d DATA --template REF.em --masks default --t TABLE.tbl` creates and opens a project in one line (Dynamo's option names; Dynamo's single-dash spellings also work); `dcp --serve` serves the view without a window; `dcp.new`/`dcp.open`/`dcp()` open the window in its own process. The earlier Tk view has been removed. `prototype/tests/test_webui.py` replays a recorded Dynamo 1.1.514 GUI session through the view's API against the same fixtures, checks the server's refusals, the one-line start and the console, and runs the HTML view in Qt WebEngine (offscreen) without script errors. | — |
| 5, 8 | Dynamo's viewers: the map viewer (`dmapview`) for templates, masks and the half-maps after an adaptive-bandpass run, the view buttons in the dcp windows, and table viewing | **Done.** `pydyn` exports `dmapview`, `dview`, `dslices`, `dtplot` (loaded lazily); the dcp window has Dynamo's view entries (View > Last computed average(s); Multireference > Adaptive filtering > Plot attained resolution FSC; template: dview; table: Plot orientations; masks: View mask / View classification mask > dview, overlay x/y/z; mask editor: live view). Each viewer runs as a separate Qt (PySide6) process. Console scripts `dmapview` and `dview`; the `gui` extra in `pyproject.toml` lists PySide6. | Not ported: View > Last computed table and All seed files, table "General info", mask editor "filtered". |
| 6 | `./<project>.exe` | **Done.** pyDynamo writes Dynamo's `.exe` byte for byte (Dynamo's five header lines, then `dynamo_execute_project <name>`); it takes no arguments. `prototype/tests/test_stage3.py` compares it with `prototype/tests/fixtures/stage3/dynamo_bin4_align_1.exe`, written by Dynamo 1.1.514. The console script `dynamo_execute_project` (`pydyn.cli:execute_main`) runs pyDynamo while the environment is active; without it the name is Dynamo's command. `dynamo_execute_project NAME --gpus 0,1` or `--gpus all` (every GPU the process sees, e.g. a Slurm job's) chooses other GPUs. | — |
| 6 | Runs on a Slurm cluster | **Done.** The dcp window's Run page proposes an `sbatch` line (GPUs, CPU cores, RAM) for the shared partitions that `sinfo` reports; the job runs `./NAME.exe`, or `dynamo_execute_project NAME --gpus all` when the project's GPU list differs from the job's GPUs. | — |
| 7, 8 | Project folder and files exactly Dynamo's, during and after the run | **Done.** pyDynamo writes no files of its own into the project: diagnostics go to stdout; the opt-in JSON report (`--report PATH` / `$PYDYN_REPORT`) is refused inside the project folder. `log.txt` is written line for line through `pydyn.dynlog` (setup banner, freeze/shift lines, engine blocks in device order, `Returning control`, assemble phases, convergence, ending, check). `gpulog.txt` is written in the working folder, as Dynamo does. During the run `temp/ite_X/intermediate_results/` gets `completedTasks_gpuProcRef_*.btbl` after every particle (exact engine) and the refined `.btbl` every 1000 particles of a GPU chunk. | Fast engine: the progress files are written once per spectra chunk, not per particle (its batches run level by level). |
| — | Anything not ported | pyDynamo raises `NotImplementedError` before writing anything. | Keep it that way: the user can then deactivate pyDynamo and run Dynamo on the same project. |

## Tests

The CPU tests need no GPU, Dynamo installation, data or FFTW, and run in CI; where they compare with Dynamo, the references are Dynamo 1.1.514's own files in `prototype/tests/fixtures/`. The GPU tests are opt-in: `PYDYN_GPU_TESTS=1 python -I -m pytest -m gpu prototype/tests`, inside a GPU job.

## Acceptance test (to build)

A scripted "Dynamo user" session, run for each documented journey (a single-reference alignment, and an alignment followed by its even/odd adaptive-bandpass project):
1. a fresh login shell, then `source .envs/pydynamo/bin/activate`;
2. Python with Dynamo's console commands, as a Dynamo user types them;
3. `dcp.new` and the GUI, driven headless, up to check and unfold;
4. `./<name>.exe`.

It then compares the whole project folder (tree, every file, `log.txt` after normalising run-dependent values) and the `.exe` bytes with Dynamo 1.1.514's own folder for the same journey.
